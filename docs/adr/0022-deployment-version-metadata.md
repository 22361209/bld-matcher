# ADR 0022: 部署版本元数据

- Status: accepted
- Date: 2026-07-30
- Owners: BLD

## Context

系统更新页以 `changes/*.json` 为事实来源，尚未发布的变更片段统一使用 `unreleased`。这个内部状态不适合作为用户可见版本号，页面需要显示当前运行代码对应的 Git 短提交号。

本机开发环境可以直接查询 Git，但 NAS 生产镜像没有安装 Git，也不会携带完整 `.git` 目录。如果运行时只调用 `git rev-parse`，生产页面只能退回“待发布”，无法标识实际部署版本。

## Decision

采用构建期生成、运行时只读的部署版本元数据：

1. Docker 构建上下文只开放 `.git/HEAD` 和本地分支引用，不把完整 `.git` 目录送入镜像。
2. 独立构建阶段解析当前提交，生成七位短提交号；最终镜像仅保留 `/app/.deployment-version`。
3. 系统更新读取器按 `BLD_APP_VERSION` 环境变量、`.deployment-version` 文件、本机 Git HEAD 的优先级解析当前版本；都不可用时显示“待发布”。
4. 每个读取器实例只解析一次版本，避免每个变更片段或页面请求重复启动 Git 子进程。
5. 只替换变更片段中的 `unreleased`；历史片段已写明的正式版本号保持不变。

## Alternatives

- **在最终镜像安装 Git 并复制完整 `.git`**：实现直接，但会增大镜像和攻击面，还会泄露不必要的仓库元数据，因此不选。
- **运行容器时挂载宿主机 `.git`**：依赖 NAS 目录结构和挂载生命周期，且运行中代码与引用可能漂移，因此不选。
- **人工维护版本文件**：容易忘记同步，并让版本号脱离实际提交，因此不选。

## Consequences

- 生产页面可明确标识镜像构建时对应的源代码提交，不依赖容器内的 Git。
- 最终镜像只包含七位提交号；构建上下文会暴露本地分支名和引用给 Docker 构建器，但不会进入最终镜像。
- 从标准主工作区构建时可以解析松散分支引用。非标准 Git worktree 或只有打包引用的源码目录可能生成 `unknown`，运行时将继续尝试环境变量或 Git 后备，最终显示“待发布”。
- 镜像版本代表构建时提交；工作区存在未提交改动时，短提交号不会描述这些改动，因此发布流程仍必须遵循先提交、再构建。

## Verification

- `tests/test_admin_update_reader.py` 覆盖环境变量、镜像版本文件、本机 Git 以及 Git 缺失、非仓库和超时的后备行为。
- Docker `version-artifact` 目标构建后，`deployment-version` 必须等于当前 Git 短提交号。
- 每次提交前运行 `uv run python scripts/verify.py`，确保项目契约和完整测试通过。
